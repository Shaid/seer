# Viewer tooling review: `tools/viewer/` across the six sibling projects

Cross-repo review of the offline asset viewer each of `crawl`, `wyrm`, `nicodemus`,
`sorcery`, `middilgard`, and `strike` ships under `tools/viewer/` (plus the
`tools/shared/` config it depends on). Read-only review — no code was changed in
any of the six repos. Companion to `docs/weaknesses.md` (framework-level gaps
found via `sorcery`/`crawl`/`middilgard`) and `docs/architecture-overview.md`
(the shared design doc all six repos carry a copy of). A parallel, separate
review is assessing what viewer logic *should* move into `@seer-project/*` — this doc
sticks to describing and assessing what exists today, not prescribing the fix.

> **Status update (2026-08-03).** The scaffold *template* this review
> describes (`packages/create-seer-app/templates/viewer/*.eta`) has since
> been substantially generalized: data-driven game/platform selectors,
> asset-type filter tabs, animation autoplay, and a generic indexed-texture +
> palette WebGL2 shader with a live editor and color-cycling were all added
> (commit `86f7057` in seer), documented in `docs/viewer.md`. **This only
> affects new projects scaffolded from today's template onward** — none of
> the six existing repos' hand-evolved viewers described below have been
> touched or migrated to pick up any of this; they still are exactly as this
> review found them. Whether/how each existing repo should adopt the new
> template capabilities is an open question, not yet decided or started.

All six repos were scaffolded from the same origin point:
`packages/create-seer-app/templates/viewer/{viewer.ts,viewer.css,index.html,shared.ts}.eta`
(217 + 140 + 52 + 35 lines). That template is the throughline for the whole
"what's common" section below — every repo's viewer is a descendant of it, at
wildly different distances.

## What's common

**1. A shared origin template.** `packages/create-seer-app/templates/viewer/viewer.ts.eta` (217 lines) is the ancestor of every one of the six viewers. It defines: the DOM id set `#list`, `#list-meta`, `#search`, `#title`, `#meta`, `#frame-info`, `#canvas-wrap`, `#zoom`, `#bg`, `#frame-strip`, `#frame-slider`, `#frame-label`, `#palette-bar`; the function shape `loadManifest()` → `renderList()` → `selectAsset()` → `drawAsset()`/`drawFullAtlas()` → `renderPalette()`; a `setHidden(el, hidden)` helper; and manual Left/Right-arrow frame stepping with wraparound (`viewer.ts.eta:197-209`). Every one of the six repos still has this exact DOM-id set and this exact function shape at its core — confirmed directly in `crawl`, `middilgard`, and via each sub-review for the rest. The template's `shared.ts.eta` (35 lines) defines `AtlasFrame`/`AtlasMeta`/`PaletteData`/`AssetEntry` and a `rgbaFromPalette()` helper that the template's own `viewer.ts.eta` never calls — see "aggregate" quality note below on how that dead export propagated.

**2. The same three-file manifest contract.** All six write, per game+platform: a flat `manifest.json` array of `{ name, sprites, hasPalette, png, ...extra }`; a per-asset `{name}.json` atlas (`{ frames: [{name,x,y,w,h}], width, height }`); and an optional per-asset `{name}.pal.json` (`{ colors: [{r,g,b}] }`). This is a completely uniform de facto standard across the family, independent of how divergent the underlying game formats are (planar Amiga bitmaps, Genesis VDP tilemaps, SNES 4bpp tiles, DOS EGA/VGA — all get reduced to this same triple before the viewer ever sees them). `strike`'s `megadrive-tilemap-assets.ts` even has an explicit comment owning this: it force-fits a tilemap render into `{frames:[...one full-image frame...], width, height}` specifically "so the generic viewer's full-atlas path... doesn't throw on a tilemap entry."

**3. All actual pixel decoding happens at build time, not at runtime.** Every viewer's canvas drawing is `ctx.drawImage(img, frame.x, frame.y, frame.w, frame.h, 0, 0, ...)` — a crop-and-blit of a PNG the pipeline already baked, plus `strokeRect` frame-boundary overlays in the "full atlas" view. `middilgard` is the one partial exception (its WebGL SAS shader and palette-cycling recomposite at runtime, and its `SceneViewer`/`MapViewer` call straight into `src/data/scene-compositor.ts`'s real `compositeScene()`), but even there the base sprite PNGs are pre-rendered.

**4. Manual-only frame scrubbing is the universal default.** A `<input type=range>` frame slider plus arrow-key stepping is present, verbatim in spirit, in every one of the six. Only `middilgard` (palette-cycle `requestAnimationFrame` loop) and `wyrm` (talk-tick 100ms interval, screen-playback 400ms interval) add any *timed* animation on top of that baseline — the other four ship exactly the template's manual-scrub-only behavior.

**5. `tools/shared/game-config.ts` wraps `@seer-project/pipeline`'s generic multi-game config — in five of six repos.** `crawl`, `wyrm`, `nicodemus`, `sorcery`, and `strike` all define `game-config.ts` as a thin narrowing of `@seer-project/pipeline`'s `GameConfig`/`PlatformConfig` (`Omit<BaseGameConfig,'id'|'platforms'> & {id: GameId; platforms: PlatformConfig[]}` — the exact same wrapper shape, independently confirmed line-for-line matching across all five) and import `defineGameConfig`, `flattenConfigs`, `resolveDataDir`, `findFileCI`, `resType`, `getGameConfig`, `getSupportedPlatforms` from it. `middilgard` is the sole exception (see Divergent §5).

**6. `@seer-project/pipeline` is the only `@seer-project/*` package touching `tools/` anywhere in the family, and even it never reaches the browser.** Grepping all six repos' `tools/viewer/` and `tools/shared/` for `@seer-project/` turns up `@seer-project/pipeline` (config helpers + `writePNG`/`writeJson`) in `crawl`, `wyrm`, `nicodemus`, `sorcery`, `strike` — always confined to the Node-side `game-config.ts`/`asset-paths.ts`/build scripts. None of the six ever imports `@seer-project/core`, `@seer-project/engine`, `@seer-project/iff`, `@seer-project/smus`, or `@seer-project/tracker` from anything under `tools/`, and **no repo's browser-side `viewer.ts` imports any `@seer-project/*` package at all** — every viewer's runtime code is vanilla DOM/fetch plus repo-local types.

**7. The same generic, partly-aspirational viewer description in `docs/architecture-overview.md`.** All six repos carry a copy of this doc's §9 "Asset Viewer" section (WebGL shader rendering, real-time palette editing, animation playback controls, music playback). It is accurate only for `middilgard`; `nicodemus`, `sorcery`, and `strike`'s sub-reviews each independently flagged the same gap between this doc and their much simpler actual viewers (no WebGL, no palette editing, no music tab, no autoplay).

**8. A template-inherited dead export.** `rgbaFromPalette()` from `shared.ts.eta` is present, verbatim, and **uncalled**, in `crawl` (`tools/viewer/shared.ts:37`), `wyrm` (`:27`), `nicodemus` (`:26`), `sorcery` (`:46`), and `strike` (`:26`) — five of six repos carry this exact dead function because it was already dead in the scaffold's own `viewer.ts.eta` (which never calls it either). `middilgard` is the only repo without it, because it never inherited `shared.ts.eta` in the first place — it built its own `manifest-types.ts` + `components/shared.ts` from scratch.

## What's divergent

**1. Number of viewers.** `wyrm` is the only repo with two entirely separate viewer apps (`viewer.ts` + `portrait.ts`, with their own `index.html`/`.css`/npm scripts). Everyone else has exactly one.

**2. Viewer-specific config file.** Only `crawl` and `middilgard` have a dedicated `tools/shared/viewer-config.ts`. `crawl`'s (64 lines: `{gameId, name, defaultPlatform, supportedPlatforms}`) is a deliberate, self-acknowledged copy of the pattern — its own header comment says it mirrors "the middilgard project's pattern." `middilgard`'s (82 lines) is the richer of the two, adding `supportedAssetTypes`, `sceneCompositor`, `paletteSelector`, `musicManifest`, `frmlRecolorMode`. `wyrm`, `nicodemus`, `sorcery`, and `strike` have no such file — their viewers either hardcode small per-game bits directly in `viewer.ts` (`wyrm`'s `RAW_MOD_GAMES` set), duplicate the game/platform table locally with an explicit "can't import Node config into the browser" comment (`nicodemus`), or don't reference game/platform-specific behavior in the viewer at all (`strike`, which is driven purely by the build-time `public/assets/index.json`).

**3. Config-vs-reality drift is a recurring but distinct failure in three different repos.**
   - `sorcery`: `game-config.ts`'s `GAME_CONFIGS` has exactly one platform entry (`amiga`, `supported: false`); `dosega` and `snes` — the platforms holding all the real decoded content — have no config entry at all, so `getGameConfig('wizardry6','dosega')` returns `undefined`, and the viewer's `DEFAULT_PLATFORM` (from `src/game-id.ts`, not `game-config.ts`) is `'amiga'`, the one placeholder.
   - `crawl`: a fully-extracted `eotb3` asset tree exists on disk (`public/assets/eotb3/dosvga/manifest.json`, listed in `public/assets/index.json`) but `src/game-id.ts`'s `GAME_IDS` and `viewer-config.ts`'s `VIEWER_CONFIGS` never mention it, so the viewer's game selector can't reach it.
   - `middilgard`: `game-config.ts`'s `GAME_PLATFORMS` fully models 9 game+platform combinations (WIME on amiga/dosvga/iigs/dosega, Spirit on amiga/cdtv, Vengeance on amiga/dosvga, Conan on amiga/dosvga, Legend on dosvga), but the viewer's platform switch is hardcoded to two values only — `currentPlatform = currentGame === 'legend' ? 'dosvga' : 'amiga'` (`tools/viewer/viewer.ts:1643`) — with no UI control to reach any of the other 6 registered combos. This is the largest build-pipeline-vs-viewer capability gap of the six.

**4. Where "real" asset generation actually happens.** In `crawl`/`wyrm`/`nicodemus`/`strike`, `tools/<game>/build-assets.ts` (wired through `@seer-project/pipeline`'s `runPipeline`) is the real, working pipeline. In `sorcery`, it is not: `tools/wizardry6/build-assets.ts` is a 34-line stub writing a hardcoded dummy 16×16/1×1 `atlas.json` that nothing reads; the real work happens in ~27 independently-run `decode-*.ts`/`dosega-*.ts`/`snes/*.ts` scripts, and a wholly separate `tools/viewer/build-manifest.ts` (90 lines, pure `readdirSync` filesystem introspection over a hardcoded `VIEWABLE_GROUPS = ['screens','sprites','maps']`) is what actually produces the manifest the viewer reads. This is a structurally different pipeline shape from the other five, not just a smaller one.

**5. Whether `game-config.ts` reuses `@seer-project/pipeline`'s config/discovery helpers.** Five of six repos import `resolveDataDir`/`findFileCI`/`defineGameConfig`/`flattenConfigs` from `@seer-project/pipeline`. `middilgard`'s `tools/shared/game-config.ts` has no `@seer-project/pipeline` import at all (confirmed: `grep -n "@seer-project/pipeline"` returns nothing) and instead reimplements the identical-in-purpose logic locally — `resolveDataDir()` (`game-config.ts:349-374`), `findFileCI()` (`:330-339`), and a `looksLikeDataDir()` helper (`:309-322`) that do the same breadth-first, case-insensitive, shallowest-match-wins search that `@seer-project/pipeline/src/config.ts`'s own `resolveDataDir`/`findFileCI` (same function names, `config.ts:167`, `:189`) already provide. `middilgard` is also the only repo of the six with zero `@seer-project/*` imports anywhere under `tools/` — its 15 files that import `@seer-project/*` are all in `src/` (the runtime engine), not the tooling layer, even though its `package.json` lists `@seer-project/core`/`engine`/`iff`/`pipeline`/`smus` as dependencies.

**6. Asset-type breadth and richness.** `middilgard` (5 asset types: IMAG/FRML/SceneViewer/MUSIC/Map, config-declared per game) and `wyrm` (5 view modes plus screens/music) are the deep ends. `nicodemus` and `sorcery` are the shallow end — a single flat list with at most two render modes (full image vs. sprite atlas), no scene/map/music concept in the viewer at all. `crawl` and `strike` sit in between: no scene/map/music tabs, but each has one bespoke extra: `crawl`'s named `groupsFile` sub-groups, `strike`'s enforced-uniform-manifest trick for non-atlas assets (tilemaps, minimaps).

**7. Live music playback exists in exactly two of six, via two unrelated mechanisms.** `wyrm`'s `music-player.ts` is a from-scratch ProTracker/FLT4 module player over raw `AudioContext`/`AudioBufferSourceNode` — Paula PAL/NTSC clock tables, hard-panned channels, its own loop-point and sample-decode math. `middilgard`'s `components/music-player.ts` instead calls straight into the real runtime engine's `SmusEngine`/`parseSmusScore` (`src/engine/smus-engine.ts`) — SMUS is decoded live by the same code the game itself uses, not reimplemented for the tool. `crawl`, `nicodemus`, `sorcery`, and `strike` have no music playback in their viewers at all, despite `strike` having `.mod`/`.wav` audio assets on disk that the pipeline writes directly (bypassing `manifestEntry`) and are therefore invisible to the viewer's category list.

**8. Real, live bugs found, each unique to its repo.** `sorcery`'s `DEFAULT_PLATFORM` defaults to the one unsupported/placeholder platform. `crawl`'s `eotb3` config is orphaned. `middilgard`'s `ViewerConfig.sceneCompositor`/`paletteSelector` fields are declared and populated in `VIEWER_CONFIGS` (`viewer-config.ts:21-23`) but never read anywhere in `viewer.ts` (confirmed: only `supportedAssetTypes`, `musicManifest`, and `frmlRecolorMode` are ever consulted, via `getViewerConfig()` call sites at `viewer.ts:661,700,743,762,1046-1047,1148-1150,1644-1648`) — dead schema fields, not dead code, but the same category of drift. `strike`'s `tools/urbanstrike/snes-build-assets.ts` claims `hasPalette: true` for two textures whose palette actually lives at a separate, unreferenced path (`palettes/ea-splash.json`), so the viewer 404s the expected `.pal.json` sidecar and silently shows no palette bar for those two assets.

## Code quality, DRY, readability

### Per-project

**crawl** — Closest to raw-template simplicity, which mostly reads as a strength (little surface area, little to go wrong), but it inherited the template's dead `rgbaFromPalette` and adds its own duplicate `ManifestEntry` type between `tools/shared/asset-paths.ts:13-18` (missing the `groupsFile` field) and `tools/viewer/viewer.ts:15-21` (has it) — two independent declarations of the same JSON contract that have already drifted apart. `tools/shared/amiga-planar.ts` stands out as the strongest single file in the repo: its palette/planar-decode comments cite exact prior wrong implementations and how they were caught (e.g. the EHB half-bright formula fix at `:43-47`), in the same spirit as this project family's "confirmed vs eliminated" docs convention. Weakest spot: zero test coverage of `viewer.ts`'s DOM/canvas logic or of `amiga-planar.ts`'s pixel math, despite the latter being the file with the most bug history.

**wyrm** — The two-viewer split is the standout DRY problem: `portrait.ts` redeclares `ManifestEntry`/`AtlasFrame`/`AtlasMeta` locally instead of importing `shared.ts` (portrait.ts:1-3), and its atlas-draw-with-highlight-rectangles/click-to-zoom hit-testing logic is a near line-for-line second implementation of what `viewer.ts:657-714` already does. Within `viewer.ts` itself, the 5-way `viewMode` union is threaded through repeated `if/else if` chains rather than a per-mode dispatch table (e.g. `:307-342`, `:836-869`), and ~20 top-level `let` bindings hold all view/selection state rather than any encapsulation — workable at this size, but `music-player.ts`'s `MusicPlayer` class (comparatively well-encapsulated) shows the file knows how to do better. Strongest asset: comment density and precision around genuinely tricky hardware behavior (Paula PAL/NTSC clock difference, signed-vs-unsigned PCM, a documented history of two specific past bugs and their fixes) — unusually high for scratch tooling.

**nicodemus** — The viewer proper is clean; the duplication problem lives one level up, across the three `build-assets.ts` files. `ManifestEntry`/`upsertManifest()` are byte-for-byte identical in `phantasie/build-assets.ts:25-45` and `phantasieii/build-assets.ts:33-53` (and near-identical again in `phantasieiii`), and copied a *fourth* time as its own independent declaration in `viewer.ts:39-44`. `AtlasFrame`/`packGridAtlas()`/`writeAtlas()` (~55 lines) are copy-pasted between `phantasie` and `phantasieii`'s build scripts, with `phantasieii/build-assets.ts:79` openly commenting "Same approach as tools/phantasie/build-assets.ts" rather than factoring it out — the duplication was noticed and left in place. On the good side, `viewer.ts:13-23`'s comment explaining why it deliberately duplicates the game/platform table rather than importing the Node-only `game-config.ts` is unusually well-justified, and it's independently corroborated by `docs/phantasie/implementation-plan.md:312-315` — the reasoning is documented twice, consistently, not just asserted once. Minor internal inconsistency: `extract-game-data.ts`'s `parseArgs` does unchecked `as GameId`/`as PlatformId` casts while `viewer.ts` properly guards with `isGameId`/`isPlatformId` predicates in the same repo.

**sorcery** — The biggest readability risk here isn't the viewer file itself (a reasonably clean 287 lines) but the surrounding pipeline's honesty gap: `build-assets.ts` looks like the real Stage 2 hook but is a stale placeholder, `game-config.ts` looks like the real per-platform config but only covers a disabled placeholder platform, and the actual logic lives in ~27 hand-run scripts plus a separate `build-manifest.ts` that nothing in `game-config.ts` references. A reader following "the" pipeline entrypoint would get no usable output. Within the decode scripts, the same "shelfPack → indicesToRGBA → writePNG + writeJson(frames) + writeJson(palette)" tail is repeated near-verbatim across most `decode-*.ts` files without a shared `writeAtlasAsset()` helper, despite `atlas-pack.ts`'s `shelfPack()` already being successfully shared. Good: `amiga-planar.ts`, `packed-pixel.ts`, and `snes-ppu.ts` all carry unusually rigorous, disassembly-offset-cited doc comments — the reverse-engineering provenance discipline is consistently strong even where the pipeline wiring isn't. Minor: `shared.ts:19-24`'s `AssetEntry` type is dead, unreferenced by anything.

**middilgard** — The best-factored codebase of the six: it's the only one to split the viewer into `tools/viewer/components/` (`map-viewer.ts`, `palette-editor.ts`, `music-player.ts`, `tile-scene-source.ts`, `shared.ts`) rather than one monolithic file, and `manifest-types.ts` is an explicit, successfully-enforced single source of truth shared between the build pipeline and the browser (its own header comment states this intent, and both `build-viewer-assets.ts` and `viewer.ts` do in fact import from it — unlike `crawl`'s parallel but drifted `ManifestEntry` duplication). It's also the only repo whose viewer calls directly into real runtime engine code rather than reimplementing logic for the tool: `compositeScene()` from `src/data/scene-compositor.ts` (`viewer.ts:13`) and `SmusEngine`/`parseSmusScore` from `src/engine/smus-engine.ts` — a clean instance of the architecture doc's "tools/ may import from src/" rule actually being used as intended. Rough edges: `viewer-config.ts`'s `sceneCompositor`/`paletteSelector` fields are dead (declared, populated, never read — see Divergent §8); the platform selector is hardcoded to two values despite `game-config.ts` modeling nine; and `game-config.ts` duplicates `@seer-project/pipeline`'s own `resolveDataDir`/`findFileCI` instead of importing them, the one place this repo is less DRY than its five siblings. `tools/README.md`'s line "SceneViewer tab (WIME only)" is also stale — `viewer-config.ts` has configured `sceneCompositor: 'excal-scen'` for Spirit and Vengeance too.

**strike** — The viewer itself is the leanest and most decoupled of the six (403 lines, never imports `game-config.ts`, driven purely by build-time `public/assets/index.json`) — a genuinely good separation given it backs the largest game/platform matrix. The DRY problems are concentrated in the build scripts: a `chunk3()` helper is copy-pasted verbatim between `tools/desertstrike/megadrive-build-assets.ts:33-37` and `tools/urbanstrike/megadrive-build-assets.ts:44-48`; the entire "find tileset/palette pairs → split by size → pack into atlases/icon strip → write catalog.json" block is duplicated near-verbatim three times (`desertstrike/megadrive-build-assets.ts:54-108`, inline in `game-config.ts:493-559` for Jungle Strike, `urbanstrike/megadrive-build-assets.ts:62-116`) — notable because the same team *did* successfully extract the closely-related tilemap and overlay-bank logic into shared helpers, so the extraction pattern was known and just wasn't applied here. `game-config.ts` is also internally inconsistent about its own stated convention: 5 of 6 registered platforms extract `buildAssets` to its own module specifically to avoid concurrent-edit conflicts on the shared config file (each says so in its header comment), but Jungle Strike's `amigaaga` variant is ~280 lines inlined directly into `game-config.ts:192-467` anyway. A real test gap: `game-config.test.ts`'s hardcoded pairs list omits `urbanstrike/snes` even though it's fully registered and has a working `buildAssets`. Strongest asset: the uniform-manifest discipline is enforced even where inconvenient (tilemaps/minimaps forced into the atlas-frame shape by explicit design, not accident), and the corpus-wide invariant counts in decoder comments ("63/63 chunks", "0 out-of-range cells across 137 maps") are a genuinely rigorous verification habit.

### Aggregate

- **The single most common DRY failure across the family is type duplication of the same manifest/atlas/palette shapes**, not logic duplication — `ManifestEntry` (or equivalent) is independently redeclared in at least two places in `crawl`, `nicodemus`, and `wyrm`'s two-viewer split, each time with slightly different optional fields, none of them validated against each other at build or test time.
- **The build-side (`tools/<game>/build-assets.ts`) is consistently where duplication is worse than the viewer side.** Every repo's `tools/viewer/viewer.ts` is a single, mostly self-contained file (or a small component set, in `middilgard`'s case); the repeated boilerplate — CLI entrypoint detection, manifest upsert, grid/shelf atlas packing — lives in the per-game build scripts, and gets copy-pasted across sibling games/platforms within the same repo (`nicodemus`'s three Phantasie games, `strike`'s three Megadrive builds) more often than it gets pushed into that repo's own `tools/shared/`.
- **Dead exports recur independently in the same shape across repos**, but trace to a single root cause (the scaffold template's own unused `rgbaFromPalette`), not five separate authors making the same mistake — worth knowing before assuming each instance needs its own fix.
- **Comment/provenance quality is uniformly high across all six** wherever the code touches a reverse-engineered binary format (palette decode, planar/bitplane math, VDP tilemap decode) — every sub-review independently flagged this as a strength, consistent with the project family's documented "confirmed vs eliminated" convention. The same rigor does not consistently extend to the viewer/config plumbing itself, where several of the "config vs. reality" drifts above (`sorcery`'s missing platforms, `crawl`'s orphaned `eotb3`, `middilgard`'s dead `ViewerConfig` fields) went unnoticed for a while specifically because nothing exercises that plumbing the way the format decoders are exercised.
- **Only `middilgard` has a real, accurate, code-verified viewer doc** (`docs/tooling/asset-viewer.md`).
